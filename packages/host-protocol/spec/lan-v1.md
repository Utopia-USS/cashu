# LAN v1: pinned pairing link and opaque carrier

The desktop host serves HTTPS only while a checked native vault is open. It advertises one per-install P-256 server SPKI pin. Its short-lived certificate has serverAuth EKU, the exact IPv4 address in its SAN, and renews with the same key. `Invite.rv` is canonical JSON with ordered keys `v`, `ip`, `port`, `spki`; v is 1, ip is a canonical RFC1918 dotted-decimal literal (loopback only in tests), port is 1..65535 and spki is 64 lowercase hex SHA-256 of DER SPKI. The native client rejects redirects and verifies host IP/SAN and pin before sending request bytes. The QR does not authorize an arbitrary URL. A paired phone retains the originally advertised IPv4 address and port. LAN v1 has no discovery or roaming protocol: if the host address changes, the phone reports unavailable until the pair is re-established through an authorized path; it never follows an unpinned replacement endpoint.

Pairing v1 sealed hello/challenge/reveal/welcome/pages are unchanged. `POST /v1/pair/exchange` takes a strict JSON envelope `{v:1,session,seq,kind,body?}`. `session` is the public 32-hex pairing session derived from the invite ephemeral key, `seq` is a strictly increasing nonnegative integer, kind is `send` with a base64url sealed message or `poll` without one. The fixed reply has kind `message` with base64url sealed body, `pending`, or `closed` with fixed code. Bodies and waits are bounded; one live invite and one consumer are admitted. Duplicate sequence only retrieves an identical cached reply; altered replay or out-of-order sequence is refused. No secret appears in a URL, query, HTTP log or fixed status.

The host persists the exact `device.added` EID and batch digest, joiner public keys/certificate and already sealed welcome/pages before append. Only an exact authenticated own-batch proof permits welcome delivery. An ambiguous append stays unknown; there is no fresh EID or second certification on retry. The mobile journal seals the original identity and versioned pending `PairingJoiner` snapshot before reveal; restore replays the original signed challenge and checks the original name, invite, device, nonce, clocks and SAS. The SAS approval expires on its original two-minute clock. After a committed append and lost welcome, `POST /v1/pair/resume` with a fresh signed device challenge can retrieve the exact cached sealed welcome/pages for a bounded post-commit interval. The host rechecks current registry trust/certificate, original event proof, vault/session/device and pin. Expired retrieval leaves the staged identity inspectable and asks for explicit recovery; it does not silently mint a new device. Resume signatures use `cashu/lan-auth/v1` with a distinct `purpose=resume` and fixed path/method.

`POST /v1/auth/challenge` returns a random 32-byte nonce and short expiry scoped server-side to vault, device, purpose and optional session. One nonce is consumed by one request. Carrier request `POST /v1/carrier` signs canonical `lanAuthBody` under `cashu/lan-auth/v1`: v, purpose, fixed path, method, vault, device, writer, segment, exact offset, SHA-256 of exact append bytes, session, nonce and expiry. The server verifies current trusted registry/certificate and request signature; append writer must equal the signer. No pairing or unregistered client may use the carrier. Request method shapes, body size, time, concurrency and rate are bounded. `list` and `read` expose opaque segment lengths/bytes only. `append` is atomic all-or-nothing at the exact current size in separate host carrier storage with durable receipt `{size,digest}`. Lost response is resolved by authenticated read at the original offset: exact bytes and size mean committed, unchanged size means absent, any other state means unknown and blocks further pushes to that remote stream until reconciled. It does not make certain local own-log writes read-only. `Transport.consistency` is `eventual` until a stronger visibility guarantee is established. Host offline, IPv6-only LAN and absent transport are explicit unavailable states; local authenticated commands continue offline.

LAN v1 bounds one opaque append or read to 72 MiB and one encoded request or reply to 100 MiB. This covers default segments and one maximum 64 MiB sealed frame with framing. An even larger valid grouped `engine.write` can produce a segment above this bound; the carrier refuses it atomically with `too_large` and leaves certain local own-log writes available offline. This explicit limit avoids changing frame/group semantics or adding a multipart protocol inside T48. Mobile peak-memory and physical-device performance remain unproven until simulator/device evidence.

No relay, iCloud, third-party storage, bank traffic or installed app service is part of LAN v1. Tests bind localhost only with synthetic private directories and test-namespaced keys. Any new context/envelope must have fixed literal vectors; old pairing and crypto vectors remain byte-identical.

`lan-auth-vector-v1.json` fixes a canonical descriptor and the exact UTF-8 bytes, Ed25519 public key and `cashu/lan-auth/v1` signatures for one append and one committed-welcome resume. Its signer seed is synthetic test material only; the vector contains no private key. Decoders must reject a noncanonical descriptor. Signature checks must fail if purpose, fixed path, method, vault, device, writer, segment, offset, append digest, session, nonce or expiry changes, or if a different signing context is used.
